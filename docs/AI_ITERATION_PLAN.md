# Primalthrum AI Iteration Plan

This document is the long-running execution plan for AI agents working on Primalthrum. Its purpose is to let a future AI continue the project without re-opening the product debate.

## Mission

Build the commercial, multi-tenant Primalthrum Agent SaaS defined in
`docs/COMMERCIAL_PRODUCT_SPEC.md`.

A customer must be able to discover the product on the public website, start a
trial, create an Agent through voice or text conversation, resolve configuration
choices inline, and immediately use the Agent in a hosted web application. The
same product must enforce subscription entitlements, usage limits, tenant
isolation, security, reliability, and commercial operations without requiring a
terminal.

## Confirmed Boundaries

First version includes:

- Web-first platform with API contracts that can later support desktop and mobile clients.
- Node server as platform API, SQLite metadata store, stream proxy, and project generator.
- Python agent runtime using LangGraph.
- Generated agents as code projects, not only database instances.
- Fixed extensible LangGraph template, not a visual graph editor.
- Runtime provider registries for LLM, memory, cache, tools, skills, and RAG.
- Development-time hot pluggability: modules are discovered and loaded before each run, not replaced mid-execution.
- RAG on/off plus vector store provider selection.
- Mock LLM and mock embedding path so the platform runs without API keys.

P1-P14 describe the completed self-hosted foundation. They are retained as
historical evidence, not as the current commercial scope.

Commercial completion requires P15-P24 and includes:

- Public website, pricing, documentation, security, status, and legal surfaces.
- Multi-user workspaces, memberships, invitations, RBAC, and tenant isolation.
- Conversational Agent creation with voice, text, inline decisions, and uploads.
- Hosted Agent applications that do not depend on generated CLI projects.
- Versioned preview, publish, audience policy, rollback, and API access.
- Real model, embedding, speech, tool, skill, memory, cache, and RAG providers.
- Trial, subscription, entitlements, credit, metering, invoice, and refund flows.
- PostgreSQL, Redis, object storage, workers, observability, and production deploys.
- Operator administration, support controls, abuse protection, and commercial
  security and release gates.

Native desktop/mobile applications, a visual graph editor, and a plugin
marketplace may follow the web SaaS launch, but web APIs and responsive design
must keep those clients compatible.

## Current State

Completed foundation:

- `agent/main.py` exposes `/stream`.
- `agent/runtime/` contains initial provider abstractions and default runtime factory.
- `server/src/app.ts` exposes stream proxy plus early agent metadata/generation APIs.
- `server/src/db/` contains SQLite schema and CLI-backed DB wrapper.
- `server/src/services/agentRepository.ts` stores agent metadata and config snapshots.
- `server/src/generators/agentProjectGenerator.ts` writes a standalone LangGraph agent skeleton.
- `web/` has a five-step operator wizard, not the required conversational SaaS.

Do not assume the current implementation is commercially complete. Treat P1-P14
as a tested foundation and use the P15-P24 queue for all new completion claims.

## Canonical Runtime Systems

### LLM

Required first-version providers:

- `mock`
- `openai-compatible` interface placeholder

Model registry shape:

```yaml
models:
  default:
    provider: mock
    model: mock-chat
  embedding:
    provider: mock
    model: mock-embedding
  planner:
    provider: openai-compatible
    model: optional-future-slot
  actor:
    provider: openai-compatible
    model: optional-future-slot
```

First implementation may only use `default` and `embedding`, but schema must not block node-level routing later.

### Memory

Boundary:

- Memory is generated by agent runs: summaries, preferences, durable facts, run state.
- RAG is user-provided external knowledge.
- Cache is repeated computation storage.

Required first-version providers:

- `NullMemory`
- `SQLiteMemory`

Write strategy:

- Write structured run summaries.
- Do not automatically store every raw user message as long-term memory.
- Expose memory listing and deletion later in the UI.

### Cache

Required first-version providers:

- `NullCache`
- `MemoryCache`
- `SQLiteCache`

Cache categories:

- Tool result cache.
- Embedding cache.
- LLM response cache, default off except mock/dev mode.

Stream events should mark cache hit/miss when cache is used.

### Tools

Tool boundary:

- A tool is a callable runtime ability with structured input and output.
- Tools require manifest metadata.
- Dangerous permissions are denied by default unless explicitly enabled.

Manifest shape:

```json
{
  "name": "file_reader",
  "description": "Read files under allowed roots",
  "input_schema": {},
  "permissions": ["fs:read"],
  "dangerous": false
}
```

Required first-version tools:

- `file_reader`
- `rag_retrieve`

Avoid shell execution tools in the first version.

### Skills

Skill boundary:

- A skill is a reusable capability package or workflow.
- A skill may depend on tools, memory, RAG, and model slots.
- A skill can register tools, but the skill itself is not a tool.

Skill package shape:

```text
skills/research/
  skill.json
  instructions.md
  workflow.py
  tests/
```

Required first-version skill:

- `research`

### RAG

First version:

- RAG can be disabled.
- RAG provider can be selected.
- Pipeline defaults are fixed.

Default pipeline:

```text
documents -> chunk -> embed -> upsert -> retrieve -> optional rerank -> context
```

Required providers:

- `NullRagProvider`
- `InMemoryVectorStore`
- Chroma adapter or interface placeholder

Interfaces to preserve:

- `EmbeddingProvider`
- `VectorStoreProvider`
- `RetrieverProvider`
- `RerankerProvider`

## Generated Agent Project Contract

Generated agent projects must be readable and independently runnable.

Target structure:

```text
generated-agents/<agent-slug>/
  README.md
  pyproject.toml
  .env.example
  src/
    main.py
    graph.py
    config.py
    nodes/
      load_context.py
      plan.py
      retrieve_optional_rag.py
      act_with_tools.py
      update_memory.py
      finalize.py
    providers/
    tools/
    skills/
    rag/
    memory/
    cache/
  tests/
```

Fixed graph:

```text
START
  -> load_context
  -> plan
  -> retrieve_optional_rag
  -> act_with_tools
  -> update_memory
  -> finalize
END
```

Configuration decides whether a node is active or no-op. Do not delete nodes when a feature is disabled.

## Platform Metadata

Persist in SQLite:

- `agents`: name, slug, path, status, description.
- `agent_configs`: enabled providers/tools/skills/models.
- `runs`: input, status, timestamps.
- `stream_events`: event type, node, payload, timestamp.
- `documents`: filename, hash, status, collection.
- `provider_configs`: provider metadata and secret references.

Do not persist:

- Tool implementation code.
- Skill implementation code.
- Provider implementation code.
- Plaintext API keys.
- Large vector payloads unless the selected local vector provider requires it.

## AI Self-Iteration Protocol

Every AI work session must follow this protocol.

### 1. Start With Brief

Write a four-line brief:

```text
目标：
证据：
约束：
下一步：
```

### 2. Pick One Main Task

Use the task selection algorithm below. Do not choose tasks by preference.

Task selection algorithm:

1. Read `## Executable Task Queue`.
2. Ignore every task with `Status: Done`.
3. Ignore every task whose dependencies are not `Done`.
4. Pick the lowest-numbered remaining task.
5. Execute only that task.
6. If the task is too large for one session, split it into smaller child tasks in this document before implementing.
7. Do not start a task from a later phase while an earlier unblocked task exists.

One session means one main task. If a fix requires another task first, stop and update the dependency chain instead of doing both.

### 3. Inspect Only What Is Needed

Read targeted files only. Prefer:

- `rg --files`
- `rg`
- short `sed` windows
- existing tests

Avoid broad full-repo scans unless the task demands it.

### 4. Write Or Update Tests First

For behavior changes:

- Add the smallest meaningful test.
- Run it and confirm it fails for the expected reason.
- Implement the smallest code change.
- Run the test again.

For pure docs changes, no code test is required; validate links/paths and formatting.

### 5. Implement In Existing Structure

Prefer existing patterns:

- Python runtime modules under `agent/runtime`.
- Node platform code under `server/src`.
- Web features under `web/src`.
- Generated project contract under `server/src/generators`.

Single file should have one clear responsibility.

### 6. Verify Minimally

Run the smallest checks that prove the task.

Common commands:

```bash
cd agent && ./.venv/bin/python -m unittest tests/test_runtime_registry.py tests/test_stream_contract.py
cd server && pnpm test && pnpm typecheck && pnpm build
cd web && pnpm lint && pnpm build
bash -n start.sh
```

Do not rerun the entire matrix after every tiny edit. Run full matrix before claiming a multi-module task is done.

### 7. Update This Plan After Each Task

Update this file when:

- A queued task is completed.
- A new blocker changes the route.
- A boundary decision changes.
- A new required backlog item is discovered.

For completed tasks, set `Status: Done` and add or update the verification evidence. Do not churn this document for every small implementation detail.

### 8. Stop Conditions

Stop and report instead of guessing when:

- The same failure repeats twice without new evidence.
- A required secret or external service is unavailable.
- A task would require changing confirmed scope.
- A test failure is caused by environment restrictions and cannot be worked around locally.

- `Inputs`: files or APIs to inspect before editing.
- `Allowed edits`: files or directories the task may change.

- `Steps`: required execution sequence.
- `Verification`: commands or checks that prove completion.
- `Status`: `Todo`, `Started`, `Done`, or `Blocked`.

## Definition Of Done

A task is done only when:

- It matches the confirmed scope.
- It has focused tests or a justified docs-only verification.
- It keeps file responsibilities clear.
- It does not introduce hidden external-service requirements.
- It keeps no-key mock mode working.
- It updates this plan only when the roadmap or status actually changes.

The historical first version is done when its original Web and standalone Agent
scenario passes. The active product goal is done only when P15-P24 pass.

## Commercial Definition Of Done

The legacy self-hosted foundation is complete when all of these are true:

- All P1-P14 executable tasks are `Done`.
- A clean checkout can install, configure, run, and verify the product using documented commands.
- A single-tenant operator can create the first admin account.
- All platform APIs except health/setup require authentication.
- Provider secrets are stored as protected references and are never returned by API.
- Dangerous tools are disabled by default and require explicit policy.
- Tool calls, config changes, runs, jobs, document indexing, and provider errors are auditable.
- Metadata and local file storage can be backed up and restored.
- Long-running generation, indexing, and run operations have job status and failure states.
- RAG documents can be indexed, reindexed, deleted, backed up, and restored.
- Generated agents can run standalone demo tasks.
- Web UI covers setup, agents, builder, runs, knowledge, settings, and error states.
- Product has operator docs, user docs, troubleshooting docs, backup/restore docs, and release notes.
- Full commercial smoke script exits 0 from a clean checkout.
- Security and release checklists are complete.
